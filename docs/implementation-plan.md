# Implementation Plan

This plan defines how the project should move from design documents to code.
The goal is enough structure to avoid drift, without building a framework before
the first toy model teaches us what is actually needed.

## Environment Policy

All Python work should use `uv`.

Canonical commands:

```bash
uv sync
uv run pytest
uv run python -m neural_abm
uv run python scripts/run_toy1.py --config experiments/configs/example.yaml
```

Project files:

- `.python-version`: Python version target. The current target is the Python
  3.14 series.
- `pyproject.toml`: package metadata, dependencies, and dev tools.
- `uv.lock`: generated by `uv sync` and committed once dependencies are
  resolved.

Do not mix `pip install` or ad hoc virtual environments into the project.
Python 3.14.4 is the latest official 3.14 maintenance release as of
2026-04-29. In this workspace, `uv` currently resolves a managed CPython 3.14.0
interpreter; if a local CPython 3.14.4 executable is installed later, `uv` can
use it as long as it is visible on PATH or selected explicitly.
When raising the Python target, first check that `torch`, `numpy`, `scipy`, and
`scikit-learn` all have compatible wheels for the target version.

## Final Module Shape

Keep reusable logic inside `src/neural_abm/`. Scripts should be thin wrappers.

Target module layout:

```text
src/neural_abm/
  __init__.py
  config.py
  core.py
  graphs.py
  logging.py
  metrics.py
  mixers.py
  toy_classification.py
  toy_pd.py
```

The intended responsibilities are:

| Module | Responsibility |
| --- | --- |
| `config.py` | Pydantic config schemas and seed/run metadata. |
| `core.py` | Common node state, simulation loop contracts, update scheduling. |
| `graphs.py` | Static graphs, dynamic peer graphs, similarity graph utilities. |
| `mixers.py` | Current home for simple peer rules, aligners, and no-social/output/latent/parameter mixers. |
| `logging.py` | Micro-state log schema and writers. |
| `metrics.py` | Task metrics and social-dynamics metrics. |
| `toy_classification.py` | Neural HK Classification environment and adapter. |
| `toy_pd.py` | Neural Spatial Prisoner's Dilemma environment and adapter. |

If peer selection, alignment, or learned edge scoring grows beyond the Toy 1
scope, split `mixers.py` into narrower modules:

```text
selectors.py
aligners.py
mixers.py
```

Do not split early just for architectural neatness. Split when Toy 2 or learned
edge functions require separate tests and configs.

Initial scripts:

```text
scripts/run_toy1.py
scripts/run_toy2.py
scripts/export_results.py
scripts/create_snapshot.py
```

Only add modules when the next experiment needs them. Avoid speculative
abstractions.

## Pre-Implementation Work Items

### 1. Toy 1 Detailed Spec

Create `docs/toy-models/neural-hk-classification.md`.

The spec should fix:

- Data-generating function.
- Agent count and private shard types.
- Probe set size for output-similarity comparison.
- Graph topology for the first run.
- Update order for each epoch.
- Mixer variants included in the first ablation.
- Metrics and plots required for a successful run.

Keep the first spec small:

```text
N agents: 50
input: R^2
output: binary class probability
model: 2 -> 16 -> 2 MLP
graph: static k-nearest or small-world
updates: synchronous
seeds: at least 5 for first comparison
```

### 2. Common Config Schema

Define one config shape before writing the runner.

Minimum sections:

```text
run:
  name
  seed
  output_dir

simulation:
  steps_or_epochs
  sync_mode
  device

agents:
  count
  model
  shard_policy

graph:
  type
  params

social:
  mixer
  peer_rule
  alpha
  threshold
  communication_budget
  alignment_scope

logging:
  micro_state
  interval
```

Use Pydantic models in `config.py` so invalid configs fail early.

### 3. Micro-State Logging Schema

Logging should be implemented before the first real experiment. Retrofitting it
later will make calibration and paper figures harder.

Minimum row-level fields:

```text
run_id
seed
t
agent_id
split_or_shard_type
output_summary
action
loss_or_reward
confidence
peer_ids
edge_weights
message_norm
param_norm
update_type
component_id
```

For Toy 1, also log:

```text
accuracy_local_probe
accuracy_global_probe
prediction_entropy
```

Raw logs should go under `experiments/runs/...`. Curated summaries should go
under `experiments/results/...`.

### 4. Minimal Module Boundary

Implement Toy 1 with these first files only:

```text
src/neural_abm/config.py
src/neural_abm/core.py
src/neural_abm/mixers.py
src/neural_abm/graphs.py
src/neural_abm/logging.py
src/neural_abm/metrics.py
src/neural_abm/toy_classification.py
scripts/run_toy1.py
```

Do not implement Toy 2 until Toy 1 has produced interpretable logs and at least
one result summary.

### 4a. Social Update Boundary

The common social-update boundary is:

```text
social_message
-> compatibility or peer scoring
-> peer selection
-> optional alignment or translation
-> typed mixer
-> commit update
```

Keep these stages separately configurable even if the first implementation
stores them in the same module. Toy 1 already shows why: aligned parameter
averaging with raw peer selection and aligned parameter averaging with aligned
peer selection are different mechanisms.

### 5. First Success Criteria

Toy 1 is good enough to move forward if:

- Runs are reproducible from a config and seed.
- Micro-state logs can reconstruct aggregate metrics.
- No-social, output mixing, latent/message mixing, and parameter averaging run
  through the same interface.
- Peer selection, alignment, and typed mixing can be ablated independently.
- At least one social mixer produces a measurable change in accuracy,
  consensus, polarization, or fragmentation.
- Parameter averaging behaves differently under same-init and independent-init
  settings, or the result is documented as a finding.

Do not require learned edge mixing for the first success gate. It belongs after
the simpler mixer taxonomy is validated.
